# How do you give each pull request its own database?

**Short answer:** Do not give each pull request its own database _server_ - give it its own logical database, cloned from a prepared template on a shared instance, or a copy-on-write branch if the engine or managed service supports it. Apply only the pull request's new migrations on top of the template, hand the environment its own scoped credentials, and drop the database when the environment is reaped. The goals are isolation between pull requests, a time to ready measured in seconds, and a cost that grows with data changed rather than data copied.

## Detail

**Why per-pull-request data at all.** Previews that share one database interfere with each other: one pull request's migration breaks another's tests, and test data from one reviewer appears in another's screens. A preview whose schema does not include its own migration is not testing the change. Per-pull-request data is what makes preview results attributable. The question is how to get it without paying for a server per preview.

**The isolation options, cheapest first:**

| Option                         | Isolation                       | Time to ready           | Cost                  | Notes                                                   |
| ------------------------------ | ------------------------------- | ----------------------- | --------------------- | ------------------------------------------------------- |
| Schema per PR, shared database | Weak - shared roles, extensions | Seconds                 | Lowest                | Breaks if the app assumes one schema or uses extensions |
| Database per PR, shared server | Good - separate catalogue       | Seconds with a template | Low                   | The usual default                                       |
| Copy-on-write branch or clone  | Good                            | Seconds, any data size  | Pay for changed pages | Neon branching, Aurora cloning, file-system clones      |
| Server per PR                  | Strongest                       | Minutes                 | Highest               | Only when testing server-level settings or upgrades     |

**Clone from a template, never migrate from empty.** Replaying every migration since the project began and then seeding data is slow and gets slower forever. Instead, a nightly job builds a template database: migrations up to `main`, plus the versioned seed data. Each preview is created from it - in PostgreSQL with `CREATE DATABASE ... TEMPLATE`, which copies the prepared database as a whole rather than rebuilding it statement by statement. Then the migration tool applies only the migrations the pull request adds, which is exactly what you want to test. See [how to seed realistic test data without copying production](./how-do-you-seed-realistic-test-data-without-copying-production.md) for what goes into the template.

**Copy-on-write makes size stop mattering.** A plain template copy still copies every byte, so a large seed takes minutes. Copy-on-write approaches share unchanged pages between the template and each clone: managed services such as Neon's branches or Aurora's fast database cloning, storage-level snapshots of a volume, or on PostgreSQL 18 setting `file_copy_method = clone` so `CREATE DATABASE ... STRATEGY = FILE_COPY` uses reflink cloning on file systems that support it, such as XFS, Btrfs, or ZFS (the default strategy since PostgreSQL 15 is `WAL_LOG`, so `FILE_COPY` must be requested explicitly). Creation time and storage then depend on what the pull request changes, not the size of the seed.

**Know the template's rules.** In PostgreSQL, a template cannot have other sessions connected while it is being copied, so the template is never used directly by any application and is refreshed by building a new one and switching a pointer, not by updating it in place. Keep two generations so a refresh never blocks preview creation.

**Credentials per preview.** Each preview gets its own role that owns its own database and can connect to nothing else, with the password generated by the controller and written to a secret in the preview's namespace. A shared superuser across previews means one preview can read or drop another's data - and makes the teardown step dangerous.

**Teardown is part of the design.** When the environment is reaped, the controller drops the database - in PostgreSQL 13 and later with `DROP DATABASE ... WITH (FORCE)`, which terminates remaining connections - and drops the role. A nightly sweep compares databases on the shared server with live environments and removes orphans. Orphaned preview databases are the cost that grows silently.

**Watch the shared server.** Many small databases on one instance share connections, memory, and I/O. Put a connection pooler in front, set a per-role connection limit, and cap the number of previews per server, adding servers as a pool rather than growing one forever. A preview running a heavy migration can slow every other preview on the host.

**Who the platform serves.** Application engineers declare "this service needs Postgres, seeded with `checkout-seed-v14`" in the environment definition; the platform owns the template pipeline, the clone mechanism, the credentials, and the teardown. Engineers should never write their own per-pull-request database scripts.

**Trade-offs.** Templates make migrations cheap to test but can hide a slow migration: a migration that takes two seconds on the seed may take an hour on production's volume. Keep a separate, deliberate check for migration duration against a production-sized copy in a controlled environment. And any per-preview approach still differs from production in data volume and skew.

## Example

```sql
-- Nightly, by the template pipeline: build a new generation, then switch the pointer.
CREATE DATABASE checkout_tpl_v14 OWNER platform_templates;
-- (migrations to main and the v14 seed are applied here, then connections closed)
ALTER DATABASE checkout_tpl_v14 WITH IS_TEMPLATE true ALLOW_CONNECTIONS false;

-- Per preview, by the environment controller. The preview server runs PostgreSQL 18
-- with file_copy_method = clone on XFS (reflinks), so FILE_COPY is a copy-on-write clone.
CREATE ROLE pr_4821 LOGIN PASSWORD 'generated-by-controller' CONNECTION LIMIT 10;
CREATE DATABASE pr_4821 TEMPLATE checkout_tpl_v14 OWNER pr_4821 STRATEGY FILE_COPY;
REVOKE CONNECT ON DATABASE pr_4821 FROM PUBLIC;

-- On reap:
DROP DATABASE pr_4821 WITH (FORCE);
DROP ROLE pr_4821;
```

```yaml
# The request, as the application team writes it inside the Environment object.
data:
  postgres:
    mode: database-per-environment # on the shared preview server pool
    template: checkout-seed-v14
    migrate: pull-request-only # apply only migrations this PR adds
    credentials: { secret: checkout-db } # role scoped to this database only
```

```text
Time to ready for the database stage, same 6 GB seed:

  migrate from empty + seed           7m40s
  CREATE DATABASE ... TEMPLATE        1m50s   full copy of the files
  template + file_copy_method=clone   0m03s   copy-on-write; size no longer matters
  + this PR's 2 new migrations        0m04s
                                      -----
  database ready                      0m07s
```

## Interview tips

- Say "logical database from a template on a shared server, or a copy-on-write branch" in the first sentence. A server per pull request is the answer that fails the cost question.
- Explain why you apply only the pull request's migrations on top of the template - it is both faster and exactly what the preview should test.
- Mention scoped credentials and forced drop on teardown; they show you have thought about blast radius and orphans.
- Name the shared-server risks: connection limits, noisy neighbours, and a pooler in front.
- Volunteer the limitation: a template hides slow migrations, so migration duration needs its own check against production-sized data.
