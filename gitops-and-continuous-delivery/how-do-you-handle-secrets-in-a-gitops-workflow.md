# How do you handle secrets in a GitOps workflow?

**Short answer:** Do not put secret material in Git at all. Commit a reference instead - an object naming a secret store path - and let a controller in the cluster fetch the value and materialise it. That keeps the declarative model intact while the secret never enters version control, and it means rotation happens in the secret store without any commit at all.

## Detail

**Why the obvious options are wrong.** Plaintext secrets in Git are visible to everyone with repository read access, forks, and clones, and are unremovable from history. Encrypted secrets in Git - sealed secrets or SOPS-style encryption - are much better and remain a legitimate choice, but they carry a real drawback: the ciphertext is committed forever, so rotating means a commit, and a future compromise of the decryption key retroactively exposes every historical secret in the repository.

**The reference model is the modern default.** An object such as an `ExternalSecret` declares where the value lives and what Kubernetes secret to create. The controller authenticates to the secret store with a workload identity, fetches the value, and creates or refreshes the Kubernetes secret. Git contains only the path, which is not sensitive.

| Approach                    | In Git     | Rotation               | Main drawback                             |
| --------------------------- | ---------- | ---------------------- | ----------------------------------------- |
| Plaintext                   | The secret | Commit                 | Unacceptable                              |
| Encrypted (SOPS/sealed)     | Ciphertext | Commit                 | Ciphertext persists in history forever    |
| Reference (external secret) | A path     | No commit - store only | Depends on a controller and a store       |
| Generated by the platform   | Nothing    | Automatic              | Only works for platform-created resources |

**The best case is that the secret never exists as an authored artefact.** When the platform provisions a database, it can generate the credential and write it straight into a Kubernetes secret, with the connection details referenced from the workload spec. Nobody types a password, nobody stores one, and rotation is a controller action. Any secret a human never sees is a secret that cannot leak through a human.

**Better still, eliminate the secret entirely where you can.** Cloud access should use workload identity rather than a stored key - EKS Pod Identity, Microsoft Entra Workload ID, or Workload Identity Federation for GKE. Database access can often use IAM authentication or short-lived certificates. The strongest version of this answer starts by asking which secrets do not need to exist, and only then how to deliver the ones that do.

**Prefer mounting over environment variables** for sensitive values. Environment variables leak into crash dumps, process listings, and logging of the process environment, and cannot be refreshed without a restart. A mounted volume, particularly via a CSI driver that fetches directly from the store, can be updated in place and never becomes a Kubernetes secret object at all.

**Guard the repository regardless.** Pre-commit secret scanning plus a CI scan, because someone will paste a token eventually. And treat any secret that reaches Git as compromised: rotate first, then clean up. Deleting the line does not remove it from history, and rewriting history does not reach forks and clones.

**Do not forget the bootstrap credential.** The controller needs to authenticate to the secret store somehow. Solving that with a stored key recreates the problem in one place; workload identity federation is what makes the chain genuinely credential-free.

## Example

```yaml
# The reference model. Git contains a path - nothing sensitive.
# external-secrets.io/v1 - v1beta1 was removed in External Secrets Operator 0.17.
apiVersion: external-secrets.io/v1
kind: ExternalSecret
metadata: { name: checkout-stripe, namespace: team-payments }
spec:
  refreshInterval: 1h # picks up rotation with no commit
  secretStoreRef: { name: platform-store, kind: SecretStore }
  target:
    name: checkout-stripe # the Kubernetes secret that gets created
    creationPolicy: Owner
  data:
    - secretKey: api_key
      remoteRef:
        key: team-payments/checkout/stripe # bounded by the tenant's store policy
        property: api_key
```

```yaml
# The store's own authentication - workload identity, not a stored key.
# This is the bootstrap problem solved properly.
apiVersion: external-secrets.io/v1
kind: SecretStore
metadata: { name: platform-store, namespace: team-payments }
spec:
  provider:
    aws:
      service: SecretsManager
      region: eu-west-1
      auth:
        jwt:
          serviceAccountRef:
            name: team-payments-secrets # federated to an IAM role scoped to
            # secret:team-payments/*
```

```yaml
# Better: the secret is never authored by a human. The platform generates the
# credential when it provisions the database and writes it to a secret.
apiVersion: platform.example.com/v1
kind: PostgresInstance
metadata: { name: checkout-db, namespace: team-payments }
spec:
  size: small
  writeConnectionSecretToRef: { name: checkout-db-conn }
---
# Best: no secret at all. Workload identity to the cloud; IAM auth to the database.
# On EKS, prefer Pod Identity for new workloads: the role is bound to this service
# account with an EKS Pod Identity association (API or IaC), so nothing sensitive
# or account-specific lives on the object. IRSA's role-arn annotation still works.
apiVersion: v1
kind: ServiceAccount
metadata:
  name: checkout
  namespace: team-payments
```

```yaml
# Mounted rather than environment variables, and fetched directly from the store
# so no Kubernetes secret object exists for it at all.
apiVersion: v1
kind: Pod
metadata: { name: checkout, namespace: team-payments }
spec:
  serviceAccountName: checkout
  containers:
    - name: checkout
      image: ghcr.io/example/checkout@sha256:9f2c8b1d...
      volumeMounts:
        - { name: secrets, mountPath: /var/run/secrets/app, readOnly: true }
  volumes:
    - name: secrets
      csi:
        driver: secrets-store.csi.k8s.io
        readOnly: true
        volumeAttributes: { secretProviderClass: checkout-secrets }
```

## Interview tips

- Lead with "commit a reference, not the value", then explain that this preserves the declarative model while keeping the secret out of history.
- Give encrypted-in-Git a fair hearing and then name its specific weakness: the ciphertext is permanent, so a future key compromise retroactively exposes everything. That nuance is what shows you have evaluated rather than followed a trend.
- The strongest move is reframing: ask which secrets need not exist. Workload identity federation and database IAM authentication remove whole categories.
- Mounted volumes over environment variables, with the reasons - crash dumps, process listings, no refresh without restart.
- Volunteer the bootstrap credential problem. Interviewers use it as the follow-up, and answering it with workload identity federation closes the loop cleanly.
